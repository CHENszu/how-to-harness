# 第 14 课：Cron Scheduler —— 让 Agent 成为不知疲倦的打工人

## 核心概念：为什么要用定时任务（Cron）？

在 s13 中，我们让 Agent 学会了“后台运行”慢命令。但无论快慢，**所有的任务都必须由你（人类）去敲回车触发**。

对于一个成熟的 Agent 来说，很多任务是不需要人盯着的，比如：
- “每天早上 9 点跑一遍全量测试”
- “每隔 30 分钟去检查一下线上 CI/CD 的构建状态”

这就是 **Cron 调度器（定时任务）** 存在的意义：
它把**“任务的调度”**和**“任务的执行”**彻底解耦。你只要定好闹钟（Cron 表达式），时间一到，调度器就会自动把任务塞给 Agent 去执行。

## 核心改造：如何实现定时调度？

在 s14 中，我们给 Harness 增加了以下四个层级的调度架构：

### 1. 任务的形态：`CronJob`
我们新增了三个工具：`schedule_cron`、`list_crons`、`cancel_cron`。
大模型调用 `schedule_cron` 时，会创建一个包含以下信息的 `CronJob` 对象：
- `cron`: 比如 `*/2 * * * *`（每两分钟执行一次）
- `prompt`: 时间到了要对 Agent 说什么（比如：“去检查一下代码规范”）
- `recurring`: 是只跑一次，还是周期性重复
- `durable`: 要不要持久化保存（存到 `.scheduled_tasks.json` 里，重启后还能继续跑）

### 2. 独立的心跳：`Cron Scheduler` (调度线程)
如果让 Agent 自己去看表，那它干活的时候就看不了表了。
所以我们在 Python 里起了一个独立的 **守护线程 (daemon)**，它的任务极其枯燥：
**死循环，每秒醒来一次，看看当前时间有没有匹配上某个 CronJob 的表达式。**
如果匹配上了，它不会直接去打扰 Agent，而是把这个任务扔进一个名为 `cron_queue` 的待办队列里。

### 3. 温柔的交付：`Queue Processor` (队列处理器)
我们又起了一个守护线程，叫 `Queue Processor`。
它就像一个贴心的秘书，盯着 `cron_queue`。但它不会强行打断 Agent 的工作，而是通过 `agent_lock` 去观察：
“Agent 现在闲着吗？如果在闲着，我就把队列里的定时任务递给它；如果它正在忙别的事，我就等等。”

### 4. 自动干活：`agent_loop` 消费
当 Agent 闲下来，`Queue Processor` 会主动拉起一轮 `agent_loop`。
Agent 的上下文里会被注入一条消息：`[Scheduled] 去检查一下代码规范`。
Agent 看到这条消息，就像收到了你敲回车的指令一样，开始调用工具干活。

## 实践操作指南

我已经为你准备好了带有中文注释的 `code_annotated.py`。

### 第 1 步：运行 s14
在终端中运行：
```bash
python s14_cron_scheduler/code_annotated.py
```

### 第 2 步：给它定个小目标
请向 Agent 发送如下指令：
> `请创建一个每 2 分钟执行一次的持久化定时任务，任务内容是：使用 bash 工具打印当前的系统时间。`

**观察重点：**
1. **注册成功**：Agent 会调用 `schedule_cron` 工具，告诉你任务创建成功了，并且你可以看到当前目录下多了一个 `.scheduled_tasks.json` 文件（持久化成功）。
2. **静静等待**：你可以什么都不输入，就干等着。
3. **自动触发**：当 2 分钟的整数倍到达时（比如 10:02, 10:04），你会突然看到终端里自动跳出了黄色的 `[Queue Processor] 拉起新一轮 Agent 执行`，接着 Agent 会自动调用 bash 工具打印出当前时间！

你可以随时用 `list_crons` 查看所有定时任务，或者用 `cancel_cron` 传入任务 ID 取消它。

学会了这一节，你的 Agent 就不再是一个“被动响应”的工具，而是一个真正可以 7x24 小时运行的“数字打工人”了！
