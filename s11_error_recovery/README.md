# 第十一课：Error Recovery —— 错误不是结束，而是重试的开始

## 核心概念：为什么需要错误恢复机制？

在前十节的开发中，我们的 Agent 已经能够处理复杂的工具调用、拥有了长期记忆并实现了动态的提示词组装。
但有一个致命的问题：**如果运行过程中 API 报错，Agent 会直接崩溃退出。**

在生产环境中（无论是调用 OpenAI 还是 Anthropic），API 错误是家常便饭。一个健壮的系统（如 Claude Code 或 Cursor）就像一台越野车，不能一遇到坑洼就熄火。我们必须对最常见的错误进行分类，并在主循环（`agent_loop`）中实现自动恢复（Error Recovery）。

**Harness 层的核心设计：分类捕获 + 自动恢复重试。**

## 核心改造：三种常见的故障模式与恢复策略

在 s11 中，我们在大模型调用的外层包裹了 `try...except`，并引入了 `RecoveryState` 来追踪恢复状态。我们主要处理以下三种故障：

### 1. 路径一：输出被截断 (`max_tokens`)
**场景**：大模型生成了一段极长的代码，但预设的 `max_tokens`（比如 8000）用完了，它的话只说到一半（`stop_reason == "length"` 或 `"max_tokens"`）。
**恢复动作**：
- **第一次触发（升级）**：不要将残缺的输出保存到历史记录中。将 `max_tokens` 升级到更高的限制（比如 64000），然后拿一模一样的上下文**重试**（Retry）。
- **后续触发（续写）**：如果 64K 都撑爆了，就把截断的内容保存下来，并自动发一条系统指令给模型：“*字数用完了。不用道歉，不用总结，请接着你刚才断掉的地方继续输出。*”（最多续写 3 次，防止死循环）。

### 2. 路径二：上下文超限 (`prompt_too_long`)
**场景**：API 报错：传入的 messages 列表太大，超出了模型的物理上下文窗口。
**恢复动作**：
触发**紧急上下文压缩 (Reactive Compact)**。在前面的课程中，我们学习过主动压缩；而这里是被动防御。代码会强行截断旧的聊天记录（例如只保留最近 5 条），然后带着截断后的上下文再次重试。如果压缩一次后依然超限，则认为无法挽救，输出错误并退出。

### 3. 路径三：临时网络故障与限流 (`429` / `529`)
**场景**：API 返回 `429 Too Many Requests`（被限流）或 `529 Overloaded`（服务器过载）。
**恢复动作**：
- **指数退避 (Exponential Backoff)**：第一次等 0.5 秒，第二次等 1 秒，第三次等 2 秒……以此类推，最多重试 10 次。
- **引入抖动 (Jitter)**：在等待时间上加上随机的微小时间差，防止多线程/多节点在同一时刻发起并发请求引发“雷暴”。
- **模型降级 (Fallback)**：如果连续遇到 3 次 529 过载错误，代码会自动尝试将模型切换为备用模型（如从 Opus 降级到 Sonnet）继续执行。
