# 第6课：短期记忆与上下文压缩 (Short-term Memory & Compaction)

在 Agent 执行复杂任务（特别是涉及不断地搜索、执行 Bash、读取文件）时，对话历史（Context）会迅速膨胀，最终超出大模型 API 的最大 Token 限制，导致程序崩溃，也就是俗称的 `Prompt too long`。

为了解决这个问题，OpenHarness 实现了一套非常优雅的**多级递进的短期记忆管理系统**。

## 💡 核心原理：多级递进压缩策略（“四步走”策略）

OpenHarness 没有采用暴力的截断或频繁请求 LLM 总结的方式，而是实现了一个精巧的四层压缩系统：

### 1. 微压缩 (Micro-compacting) —— 最廉价的瘦身（扔掉旧草稿）
这是系统的第一道防线。在不调用大模型的情况下，直接对历史消息进行处理。
- **机制**：针对 `read_file`, `bash`, `grep`, `web_search` 等工具产生的庞大输出，系统只会保留最近的 N 个结果（默认 5 个）。
- **处理方式**：将更早的工具输出内容直接替换为占位符 `[Old tool result content cleared]`，从而极大地节省了 Token，同时又保留了工具被调用过的“历史痕迹”。

### 2. 文本折叠 (Context Collapse) —— 机械裁剪
如果微压缩后，上下文依然很长，系统会针对超长文本块（超过 2400 字符）进行机械裁剪。
- **机制**：保留文本的前 900 个字符和后 500 个字符，中间部分直接替换为类似 `...[collapsed 1000 chars]...` 的提示。这确保了大模型能看到文本的开头和结尾（通常包含结论或报错信息），而不被中间的冗长内容淹没。

### 3. 会话内存持久化 (Session Memory Compaction) —— 提取结构化状态
为了防止在对话变长时丢失当前的任务焦点，系统在每一轮对话结束后，都会在本地磁盘（`session-memory` 目录下）保存一个 Markdown 格式的会话快照。
- **快照内容**：包含当前的目标 (Goal)、下一步计划 (Next Step)、已验证的工作 (Verified Work) 以及最近对话的文本摘要（每条消息被缩略到 220 字符以内）。
- **用途**：当系统需要进行压缩时，如果对话历史不是很长，系统会直接读取这个文件并注入到提示词中，避免调用 LLM 进行全量总结。

### 4. 全量 LLM 总结 (Full LLM Compaction) —— 最后的手段（写便签纸）
当 Token 数逼近模型上下文窗口的阈值（如预留 13,000 Token 的安全缓冲期），或者当大模型 API 返回了 `Prompt too long`（上下文长度超出限制）的错误时，系统会强制触发全量压缩：
- **保留最近上下文**：默认保留最近的 6 条消息（`preserve_recent=6`）不做任何修改，确保当前对话的绝对连贯性。
- **调用模型总结**：将更早的历史消息发送给 LLM（如 Claude 或 DeepSeek），并附带一段极其严格的 Prompt：
  - 强制要求模型**不能调用任何工具**（防止在总结时产生幻觉执行操作）。
  - 要求提取：用户的原始意图、技术决策、修改过的文件及行号、所有报错及修复方案。
- **上下文替换**：将 LLM 生成的 Summary（总结）以及从旧消息中提取的附件（Attachments，如活跃工件、最近读取的文件等）拼接成一条新的 User Message，替换掉所有旧的对话历史。

**总结**：OpenHarness 通过**微压缩（清空旧工具输出）** -> **文本折叠（中间截断）** -> **会话快照（提取结构化状态）** -> **LLM 全量总结（深度提炼）** 这一套“四步走”策略，优雅地解决了长对话导致的上下文超限和任务焦点丢失的问题。

## 🛠️ 本节重点代码结构

为了更好地组织代码，我们进行了模块化拆分：

- `tools.py`: 存放 `BaseTool` 抽象类，以及本节配备的 `WebSearchTool` 和 `BashTool`。
- `engine.py`: 核心引擎！包含负责处理工具调用的 `agent_loop`，以及本节的核心：`MemoryManager`（内存管理器）。
- `main.py`: 运行入口，供你输入测试指令。

## 🚀 运行与测试

```bash
python main.py
```

你可以尝试给它下达一个需要多轮探索的复杂任务，观察它如何在 Token 逼近阈值时，自动触发“微压缩”甚至“写便签”。
