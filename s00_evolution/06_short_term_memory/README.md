# 第6课：短期记忆与上下文压缩 (Short-term Memory & Compaction)

在 Agent 执行复杂任务（特别是涉及不断地搜索、执行 Bash、读取文件）时，对话历史（Context）会迅速膨胀，最终超出大模型 API 的最大 Token 限制，导致程序崩溃，也就是俗称的 `Prompt too long`。

为了解决这个问题，OpenHarness 实现了一套非常优雅的**多级递进的短期记忆管理系统**。

## 💡 核心原理：多级递进压缩策略（“四步走”策略）

OpenHarness 没有采用暴力的截断或频繁请求 LLM 总结的方式，而是实现了一个精巧的四层压缩系统：

### 1. 微压缩 (Micro-compacting) —— 最廉价的瘦身（扔掉旧草稿）
这是系统的第一道防线。在不调用大模型的情况下，直接对历史消息进行处理。
- **机制**：针对 `read_file`, `bash`, `grep`, `web_search` 等工具产生的庞大输出，系统只会保留最近的 N 个结果（默认 5 个）。
- **处理方式**：将更早的工具输出内容直接替换为占位符 `[Old tool result content cleared]`，从而极大地节省了 Token，同时又保留了工具被调用过的“历史痕迹”。

### 2. 文本折叠 (Context Collapse) —— 机械裁剪
如果微压缩后，上下文依然很长，系统会针对超长文本块（超过 2400 字符）进行机械裁剪。
- **机制**：保留文本的前 900 个字符和后 500 个字符，中间部分直接替换为类似 `...[collapsed 1000 chars]...` 的提示。这确保了大模型能看到文本的开头和结尾（通常包含结论或报错信息），而不被中间的冗长内容淹没。

### 3. 会话内存持久化 (Session Memory Compaction) —— 提取结构化状态
为了防止在对话变长时丢失当前的任务焦点，系统在每一轮对话结束后，都会在本地磁盘（`session-memory` 目录下）保存一个 Markdown 格式的会话快照。
- **快照内容**：包含当前的目标 (Goal)、下一步计划 (Next Step)、已验证的工作 (Verified Work) 以及最近对话的文本摘要（每条消息被缩略到 220 字符以内）。
- **用途**：当系统需要进行压缩时，如果对话历史不是很长，系统会直接读取这个文件并注入到提示词中，避免调用 LLM 进行全量总结。

### 4. 全量 LLM 总结 (Full LLM Compaction) —— 最后的手段（写便签纸）
当 Token 数逼近模型上下文窗口的阈值（如预留 13,000 Token 的安全缓冲期），或者当大模型 API 返回了 `Prompt too long`（上下文长度超出限制）的错误时，系统会强制触发全量压缩：
- **保留最近上下文**：默认保留最近的 6 条消息（`preserve_recent=6`）不做任何修改，确保当前对话的绝对连贯性。
- **调用模型总结**：将更早的历史消息发送给 LLM（如 Claude 或 DeepSeek），并附带一段极其严格的 Prompt：
  - 强制要求模型**不能调用任何工具**（防止在总结时产生幻觉执行操作）。
  - 要求提取：用户的原始意图、技术决策、修改过的文件及行号、所有报错及修复方案。
- **上下文替换**：将 LLM 生成的 Summary（总结）以及从旧消息中提取的附件（Attachments，如活跃工件、最近读取的文件等）拼接成一条新的 User Message，替换掉所有旧的对话历史。

**总结**：OpenHarness 通过**微压缩（清空旧工具输出）** -> **文本折叠（中间截断）** -> **会话快照（提取结构化状态）** -> **LLM 全量总结（深度提炼）** 这一套“四步走”策略，优雅地解决了长对话导致的上下文超限和任务焦点丢失的问题。

## 🌰 通俗案例：四层“剥洋葱”压缩法

为了直观理解这四层机制，我们假设你和 LLM 进行了 30 轮对话，主要在排查一个 Python 脚本的报错。
目前的对话历史大致如下（已经达到了 Token 警告线）：

1. **用户**：帮我看看 `app.py` 为什么报 `KeyError: 'user'`。
2. **LLM**：好的，我用 `read_file` 读一下 `app.py`。
3. **工具返回**：*[返回了 `app.py` 完整的 500 行代码...]*
4. **LLM**：看样子是少传了字典键，我用 `bash` 跑一下测试。
5. **工具返回**：*[返回了 1000 行的 Pytest 报错堆栈...]*
6. **LLM**：报错很长，我修改了第 20 行，加了 `.get('user')`。
7. ... *(经过了反复的读文件、改代码、跑测试)* ...
29. **用户**：现在不报错了，但日志输出太长，帮我把日志格式化一下。
30. **LLM**：没问题，我来修改日志配置。

此时，LLM 的脑容量（Token）快爆了，触发了**压缩机制**：

### 第一层：微压缩 (Micro-compaction)
**核心动作：扔掉过期的“大块头”工具结果，只留最新的。**

系统扫描历史记录，发现有很多次 `read_file` 和 `bash` 的超长输出。
- 第 3 轮的 `app.py` 500 行代码？**删掉！**
- 第 5 轮的 1000 行报错堆栈？**删掉！**
- 第 28 轮最新的测试结果？**保留**。

**微压缩后的历史：**
1. **用户**：帮我看看 `app.py` 为什么报...
2. **LLM**：好的，我用 `read_file`...
3. **工具返回**：`[Old tool result content cleared]` （变成了一句占位符，瞬间省了几千 Token）
...
29. **用户**：现在不报错了...
30. **LLM**：没问题，我来修改...

*如果此时 Token 降下来了，压缩就结束了。如果还不够，进入下一层。*

### 第二层：上下文折叠 (Context Collapse)
**核心动作：掐头去尾，中间变成省略号。**

假设有一轮对话，LLM 写了一篇长达 3000 字的详细原理解释，微压缩对普通文本是不起作用的。
系统会对超长文本进行“折叠”：保留开头的 900 个字符和结尾的 500 个字符。

**折叠后的历史：**
...
15. **LLM**：关于这个问题，原理是这样的... *[保留前900字]*
`...[collapsed 1600 chars]...` （中间的废话被干掉了）
最后总结来说，必须用安全获取法。*[保留后500字]*
...

*如果 Token 还是超标，进入第三层。*

### 第三层：会话记忆替换 (Session Memory Compaction)
**核心动作：拿事先写好的“工作交接单”，直接换掉旧聊天记录。**

系统平时会在后台默默写一份 Markdown 格式的“短期记忆”。系统决定把**前 25 轮对话全部抹掉**，替换成这份摘要，只保留最近的 5 轮对话（第 26-30 轮）。

**替换后的历史：**
1. **系统提示**：`[Session memory summary from earlier...]`
   - **目标**：修复 `app.py` 里的 `KeyError`。
   - **已验证工作**：第 20 行已经用 `.get('user')` 修复了报错。
   - **活跃文件**：`app.py`。
   - **近期对话简述**：用户求助 -> LLM 读代码 -> LLM 跑测试 -> 问题修复。
2. *(原来的前 25 轮对话彻底消失)*
3. **(保留) 第 26 轮**：LLM：测试通过。
...
5. **(保留) 第 29 轮**：用户：现在不报错了，帮我把日志格式化一下。
6. **(保留) 第 30 轮**：LLM：没问题，我来修改日志配置。

*这招非常省钱（不用调大模型），但如果这份静态摘要信息太简略或者 Token 还是不够，就会使出最终绝招。*

### 第四层：全量 LLM 总结 (Full LLM Compaction)
**核心动作：请 LLM 亲自写一份极其详尽的“案情卷宗”，然后带着关键“附件”重新开始。**

系统会把前面的长对话发给 LLM，让它写一份结构化的总结。为了防止 LLM 忘掉当前的工作焦点，还会带上几个**附件（Attachments）**。

**最终压缩后的新会话长这样：**

1. **系统边界标记**：
   `[Compact boundary marker]`
   之前的对话已压缩，请根据以下总结继续工作。

2. **LLM 生成的卷宗 (Summary)**：
   - **主要请求**：排查 `app.py` 报错，并在修复后格式化日志。
   - **修改的文件**：`app.py` 第 20 行。
   - **解决的问题**：因缺少字典键导致崩溃，已通过安全获取修复。
   - **待办事项**：需要修改日志配置格式。

3. **关键附件 (Attachments)**：（防忘备忘录）
   - `[Compact attachment: task_focus]` 当前目标：格式化日志。下一步：编辑日志配置文件。
   - `[Compact attachment: recent_files]` 最近看过的文件：`app.py`。

4. **最近的原话 (Messages to keep)**：
   - **用户**：现在不报错了，但日志输出太长，帮我把日志格式化一下。
   - **LLM**：没问题，我来修改日志配置。

经过这四层“榨汁”，几十轮啰嗦的对话变成了：**一份结构化的高清总结 + 几个当前工作状态的附件标签 + 最近几句原汁原味的对话。** LLM 看到这个新的开头，马上就能接上思路说：“好的，我现在就去改日志配置。”

## 🛠️ 本节重点代码结构

为了更好地组织代码，我们进行了模块化拆分：

- `tools.py`: 存放 `BaseTool` 抽象类，以及本节配备的 `WebSearchTool` 和 `BashTool`。
- `engine.py`: 核心引擎！包含负责处理工具调用的 `agent_loop`，以及本节的核心：`MemoryManager`（内存管理器）。
- `main.py`: 运行入口，供你输入测试指令。

## 🚀 运行与测试

```bash
python main.py
```

你可以尝试给它下达一个需要多轮探索的复杂任务，观察它如何在 Token 逼近阈值时，自动触发“微压缩”甚至“写便签”。
