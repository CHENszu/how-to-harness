# 第 16 课：Team Protocols — 队友之间要有约定

## 核心概念：为什么要给队友定规矩？

在 s15 中，我们让老大和小弟（队友）用“文件邮箱”互发消息。但这就像现实中发微信一样，**非常松散**。

假设出现下面两个场景：
1. **老想让小弟下班（关机）**：老大直接把小弟的线程强行杀掉（Kill）。结果小弟正在写文件，写了一半被杀了，留下一堆烂摊子。
2. **小弟想做危险操作（比如删库重构）**：小弟觉得这事很重要，发微信跟老大说“我要重构数据库了哈”，然后不等老大回复，直接就动手了。

这就暴露出缺乏**结构化协议（Protocols）**的致命问题。
队友之间不能只发文本聊天，还需要有一套**请求-响应（Request-Response）**的握手机制。

---

## 核心改造：如何实现结构化握手？

在 s16 中，我们给 Harness 增加了状态机，把“发微信”升级成了“走工单系统”。

### 1. 状态追踪器 (ProtocolState)
每当发起一个请求（比如关机请求、计划审批请求），系统会在内存里创建一个 `ProtocolState` 工单。
工单里有一个唯一的 `request_id`（比如 `req_001`），并且状态是 `pending`（待处理）。

### 2. 标准的关机握手 (Shutdown Protocol)
现在老大想让小弟下班，不能直接杀线程了：
1. **老大发工单**：老大调用 `request_shutdown` 工具，发一条类型为 `shutdown_request`、带有 `req_001` 的消息给小弟。
2. **小弟收工单**：小弟在空闲时（idle loop）收到消息，发现这是个关机请求。它会先把自己手头的事收尾。
3. **小弟盖章回复**：小弟发出一条 `shutdown_response` 消息，附带同样的 `req_001`，并标记 `approve=True`。
4. **老大归档**：老大收到回复，通过 `req_001` 找到之前的工单，把状态改成 `approved`。小弟这才安心闭眼（退出线程）。

### 3. 计划审批握手 (Plan Approval Protocol)
如果小弟接到一个复杂任务，我们可以要求它“先提交计划，等老大审批后再动手”：
1. **小弟提交计划**：小弟调用 `submit_plan` 工具，把写好的重构计划发给老大（`req_002`）。
2. **老大审批**：老大看了计划，觉得没问题，调用 `review_plan` 工具，同意 `req_002`。
3. **小弟动手**：小弟收到同意的回复，才真正开始调用 `bash` 或者 `write_file` 去干活。

## 实践操作指南

我已经为你准备好了带有中文注释的 `code_annotated.py`，底层调用逻辑完全兼容你配置的 DeepSeek 接口，防 GBK 乱码和防崩溃机制也都妥妥地在里面。

### 第 1 步：运行 s16
在终端中运行：
```bash
python s16_team_protocols/code_annotated.py
```

### 第 2 步：体验“走流程”的关机
请向 Agent（老大）发送如下指令：
> `请召唤一个名为 alice 的队友。让她随便写个文件。等她写完后，请走正规的协议流程让她关机（request_shutdown）。`

**观察重点：**
你会清晰地看到终端里打印出状态机的流转过程：
1. `[Inbox] 老大收到 ... shutdown_response`
2. `[Protocol] req_xxx 状态变为 approved`
3. `[Team] 队友 alice 体面退出`

这就不是简单的“发消息”了，这是有借有还、状态可追踪的企业级协同协议！
