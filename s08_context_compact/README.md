# 第八课：Context Compact —— 记忆清理术（四层压缩策略）

## 核心概念：为什么要压缩上下文？

在前面的课程中，我们的 Agent 学会了调工具、做计划、派小弟、翻技能书。
但随着任务的深入，比如它连续读了 30 个文件，跑了 20 条 bash 命令。这些文件的内容和命令的输出，全部堆积在 `messages` 列表中。

大模型的上下文窗口（Context Window）是有限的（也是很贵的）。如果满了，API 会直接报错 `prompt_too_long`，Agent 当场罢工。
为了让 Agent 能在大型项目中长时间、无限轮次地工作，我们必须引入**上下文压缩机制**。

**Harness 层的核心设计原则：便宜的先跑，贵的后跑。**

---

## 核心改造：四层压缩流水线 (Four-Layer Compaction)

在 s08 中，我们在每一次发请求给大模型之前，插入了一条由 4 个步骤组成的“清洗流水线”：

### L1 (最便宜): snip_compact (裁减中间对话)
**场景**：你已经和 Agent 聊了 80 轮。最前面的“帮我建个文件夹”这种废话还在占地方。
**做法**：如果消息总数超过 50 条，代码会强行保留**最初的 3 条**（系统设定和目标）和**最近的 47 条**（当前工作上下文），把中间的几十条直接删掉，换成一句占位符 `[snipped 30 messages]`。
*(0 成本，纯数组切片)*

### L2 (很便宜): micro_compact (旧工具结果占位)
**场景**：Agent 刚刚连续读了 10 个文件。第 1 个文件到第 7 个文件的内容（可能好几万字）还在上下文里，但现在其实只需要看最后 3 个文件。
**做法**：代码会去扫描，只保留最近 3 次工具调用的完整结果。更早的工具结果，如果很长，直接替换为一句话 `[Earlier tool result compacted. Re-run if needed.]`。
*(0 成本，正则或条件匹配)*

### L3 (略微费劲): tool_result_budget (大结果落盘)
**场景**：哪怕只保留最近 1 次的结果，但这次 Agent 脑抽了，执行了 `cat webpack.bundle.js`，一次性输出了 200 万字，直接撑爆内存。
**做法**：统计当前回合所有工具结果的总大小。如果超过 200KB，就按大小排序，把最大的结果**保存到本地硬盘的临时文件夹里**。然后告诉大模型：“输出太长了，我存到硬盘的某某路径了，你自己去读前 2000 个字预览吧。”
*(0 成本 API，但涉及本地硬盘读写)*

### L4 (最贵): compact_history (LLM 全量摘要)
**场景**：前 3 招全用完了，上下文还是太长（超过了 THRESHOLD）。这时候只能动真格的了。
**做法**：
1. 先把完整对话原封不动保存到硬盘的 `.transcripts/` 目录（防止数据彻底丢失）。
2. 调用一次大模型 API（花钱），要求它：“请总结一下前面的对话，保留当前目标、已改文件和剩余工作。”
3. 把长达几十轮的 `messages` 列表全部清空，只留下一条消息：`[Compacted] 总结内容...`。
*(1 次额外的 API 调用)*
