# 第 13 课：Background Tasks —— 告别“傻等”，慢操作放后台

## 核心概念：为什么要用后台任务？

在前面的课程中，我们的 Agent 执行所有工具（尤其是 `bash` 命令）都是**同步阻塞**的。
就像你把衣服扔进洗衣机，然后你就一直傻站在洗衣机面前，直到 30 分钟后洗完才去干别的事。

对于 Agent 来说：
- 执行 `cat README.md` 是毫秒级的，等一下没关系。
- 但如果执行 `npm install`、`pip install torch` 甚至跑一个完整的 E2E 测试，可能需要 5-10 分钟。
如果 Agent（大模型）一直卡在这里“傻等”，不仅浪费时间，还白白占用了资源。

**Harness 层的解法：异步后台线程 + 结果通知注入。**
把慢命令丢给操作系统的后台线程去跑，Agent 可以立刻收到一个占位符并继续干别的事（比如去读其他的代码文件），等慢命令跑完后，系统再把结果“悄悄”塞进对话历史中通知 Agent。

---

## 核心改造：如何实现后台机制？

在 s13 中，我们对工具系统和主循环做了以下 3 点核心改造：

### 1. 怎么判断一个命令慢不慢？（触发条件）
我们给了大模型决定权，但也做了一个兜底。
- **显式请求**：大模型可以在调用 `bash` 工具时，主动传入一个新增的参数 `run_in_background=true`。
- **启发式兜底**：如果大模型忘了，我们在 Python 里写了一个 `is_slow_operation` 函数，只要命令里包含 `install`、`build`、`test` 等关键词，我们就强行把它当做慢命令。

### 2. 后台是怎么跑的？（执行机制）
当识别到是后台任务时：
1. Python 会分配一个独立的 ID（如 `bg_0001`）。
2. 创建一个独立的 `threading.Thread`（守护线程）去执行这个 `bash` 命令。
3. **立刻**给大模型返回一句话：`[后台任务 bg_0001 已启动] 结果将在完成后通知你。`
这样，大模型的这一次工具调用就结束了，它可以继续思考下一步该干嘛。

### 3. 跑完怎么告诉大模型？（通知注入）
后台线程跑完后，会把结果存到一个全局的 `background_results` 字典里。
在 `agent_loop` 每一轮询问大模型之前，系统会去这个字典里“收菜”（`collect_background_results`）。
如果发现有任务跑完了，就把结果包装成特定的 XML 格式（`<task_notification>`），作为普通的文本追加到对话历史中，让大模型看到。

```xml
<!-- 通知格式示例 -->
<task_notification>
  <task_id>bg_0001</task_id>
  <status>completed</status>
  <command>pip install torch</command>
  <summary>Successfully installed torch-2.0.1...</summary>
</task_notification>
```

## 实践操作指南

我已经为你准备好了带有中文注释的 `code_annotated.py`，并在其中故意给后台任务加了一点睡眠时间，以便你能清楚地观察到异步现象。

### 第 1 步：运行 s13
在终端中运行：
```bash
python s13_background_tasks/code_annotated.py
```

### 第 2 步：体验“边洗衣服边扫地”
请向 Agent 发送这样一个复杂的指令：
> `请在后台运行 pip list（请使用 run_in_background 参数），并在等待它完成期间，去读一下 README.md 文件。`

**观察重点：**
1. **启动后台任务**：你会看到终端打印出绿色的 `> 使用工具: bash`，接着是黄色的 `[后台启动] 分配了 bg_0001`。
2. **Agent 没卡住**：紧接着你会发现，Agent 没有等 `pip list` 跑完，而是立刻打印了 `> 使用工具: read_file` 去读了文件。
3. **收到通知并结合**：过几秒后，后台线程跑完了，终端会打印 `[注入] 1 个后台任务通知`。最后，Agent 的大脑同时接收到了“读取文件的结果”和“后台任务跑完的通知”，并给你做出了完美的综合回答。

通过这节课，你的 Agent 真正具备了“多线并发”处理复杂工程任务的能力！
